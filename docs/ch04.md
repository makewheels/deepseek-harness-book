# 第4章 一切皆插件

> **阅读提示**
> 本章讲 dsh 的立身之本：插件机制。读完你会明白"一切皆插件"到底彻底在哪，为什么零件可以随便换，以及"agent 给自己做手术"的底气从何而来。地基是一个叫 Cordis 的框架，本章只讲它的大白话版本。

## 想换个零件，不用拆车

先立个靶子。假设你想给 AI 助手换个大脑供应商——不用 DeepSeek 了，换别家模型。两种做法的对照非常鲜明（表4-1）。

**表4-1 换个大脑：两种做法**

| | 传统产品 | dsh |
|---|---|---|
| 谁动手 | 官方工程师改核心代码 | 你改一份配置 |
| 流程 | 修改、编译、发版 | 拔下旧适配器，插上新适配器 |
| 你的角色 | 等更新 | 自己动手 |

dsh 敢这么干，是因为**模型适配器只是一个插件**——官方架构文档里，"添加模型提供方"这件事就一句话：在 `ctx.llm` 服务上注册它的适配器。

工具、界面、审批策略，甚至驱动循环的"司机"，全是同等待遇。这套机制的地基，是一个叫 **Cordis** 的插件框架。

## Cordis：整体搬进来的地基

dsh 没有自己发明插件机制，而是把 Cordis 整个"vendor 化"——源码原样搬进仓库的 `vendor/cordis`，不通过 npm 依赖远端的包。

这么做的好处官方写得很直白：harness 完全拥有这一层框架——**可审计、可打补丁、版本钉死**。想读地基的源码，它就在仓库里：[vendor/cordis](https://github.com/deepseek-ai/deepseek-harness/tree/master/vendor/cordis)。

Cordis 本身是一个 TypeScript 插件框架，为需要"显式依赖注入、作用域服务、生命周期管理的清理"的应用而生。翻译成大白话就是三句：你依赖什么必须明说；服务按名字挂在共享总部上；你干过的每件事都必须能撤销。

官方的 [Cordis 入门](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-primer.zh.md)把整个框架归纳成五个概念（表4-2），本章剩下的内容就是逐个把它们讲成人话。

**表4-2 Cordis 的五个核心概念**

| 概念 | 官方一句话 | 大白话 |
|---|---|---|
| 插件（Plugin） | 实现 Service 的对象 | 来入职的员工：一个函数或一个类，被挂载就开始干活 |
| 上下文（Context） | 服务的容器 | 共享总部，服务占据稳定的 `ctx.<键>` |
| `inject` | 声明服务依赖 | 入职时申报合作对象，到齐了才开工 |
| 类型化事件 | 通信机制 | 总部广播，频道名和消息格式都提前声明 |
| 可逆副作用 | 注册即 effect | 登记在册的一切，离职时原样撤销 |

## 挂载与卸载：入职与离职

一个插件的一生只有两个动作（图4-1）：**挂载（入职）**和**卸载（离职）**。

![插件的挂载与卸载](images/fig4-1-plugin-lifecycle.svg)

**图4-1 插件的挂载与卸载**

入职时，插件在总部办最多三件事：挂一个带名牌的服务、加几个广播群、把注册事项记进台账。离职时，这三件事被逐条撤销，总部恢复原状，像这个人从没来过。

仓库里还配了一套七课的中文 [Cordis 教程](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-tutorial/index.zh.md)，本章结尾的实验就从第 1 课开始。

## Service：带名牌的前台，认牌不认人

服务按名字挂在总部上，这个名字就是一个稳定的 `ctx.<键>`。想找谁办事直接报名字，不用管台子后面坐的是谁。表4-3 列几个真实的（第 3 章见过）。

**表4-3 几个真实的服务键**

| 键 | 管什么 |
|---|---|
| `ctx.sessions` | 会话日志（会议纪要） |
| `ctx.systemPrompt` | 开场白组装：提示词片段 + 工具清单 |
| `ctx.tools` | 工具登记与带把关的执行 |
| `ctx.agents` | agent 接待口，所有插件找 agent 都走它 |
| `ctx.agentLoop` | 司机：默认的"想一步→干一步"循环实现 |
| `ctx.llm` | 消息与流式词汇表，以及模型适配器的接口 |

第 3 章那句"只认前台、不认司机"说的就是这个。教程里还有一句值得抄下来：**消费方只指定 `tools` 之类的能力名，不导入提供方，所以配置可以选择提供方，而无需修改消费方。**

服务的另一半是依赖申报。插件用 `inject` 列出自己需要的服务，Cordis 会让它停在 PENDING 状态等，直到每项服务都就位——**加载顺序由服务依赖表达，而不是文件里的位置**。

这个设计有两个有趣的推论：

- **顺序无所谓。**把配置文件里两个插件的顺序对调，运行结果不变；干脆删掉提供方，消费方也只是安静地等，不崩溃、不半运行。
- **依赖被持续跟踪。**`inject` 不是一次性的开机检查。运行中某项服务消失（提供方被卸载或热替换），依赖它的插件会跟着卸载，等服务回来再重新加载。这防的是"运行中的消费方攥着一个已失效服务的引用"。

第二条正是"热换件"的地基——换了零件，所有依赖它的人自动重新对接。

## 类型化事件：总部广播，但频道受管

广播机制：有人发消息，所有订阅了这个频道的人都收到。但 Cordis 的广播不是乱喊话——每个频道的名字和消息格式都提前在类型系统里声明，发的人和听的人写错了会被当场抓出来。

更严格的是，每个事件都有一种**分发模式**，它是事件公开约定的一部分，发和听必须对齐（表4-4）。

**表4-4 事件的四种分发模式**

| 模式 | 怎么走 | 有返回值吗 | 典型用途 |
|---|---|---|---|
| `emit` | 监听者按注册顺序观察，不等待 | 无 | 纯通知 |
| `waterfall` | 沿一排负责人传递，每层可包装或短路 | 有 | 审批、拦截、改写 |
| `parallel` | 所有监听者并发执行 | 无 | 必须等大家都完成的活 |
| `serial` | 按序执行并等待，第一个有效回答胜出 | 有 | 决策前的最后关卡 |

其中一种要单独讲：**waterfall（瀑布）**。消息像传令一样经过一排负责人，每人除了收到消息，还收到一个 `next()`——调用它才会传给下游，下游的结果回到你手里，你还可以包装一层再往外传；不调用它直接返回，链条就此短路，官方管这叫"否决"。

于是有一条纪律：**只负责观察或标注的监听器必须调用 `next()`**；不调用而直接返回，代表"这个决策归我"。否则一个粗心的日志监听器，就能悄悄吞掉所有下游行为。

waterfall 在 dsh 里用在哪？第 6 章的审批流就是：`approval/request` 事件允许策略代替用户作答。`agent/request` 允许插件替换模型调用的配置。下一章的 pre-step 关卡、模型请求、三道工具关卡，也全是 waterfall。

## 可逆副作用：dsh 最硬的规矩

Cordis 有条铁律：**每个注册都是可逆的副作用**。

提示词片段、工具 schema、适配器、提供方、监听器，全都要通过注册安装；卸载和热重载时，它们按预期撤销。挂载即注册、卸载即撤销——这对对称动作，是一切"可替换"承诺的底座。

多数时候你不用亲手写撤销逻辑，因为**内置的注册 API 本身已经是 effect**（表4-5）。

**表4-5 已经被管起来的注册**

| 动作 | 卸载时会发生什么 |
|---|---|
| `ctx.on` 监听事件 | 监听器被移除 |
| `ctx.plugin` 挂子插件 | 子插件随父插件一起释放 |
| 服务注册 | 提供方卸载时服务被摘除 |
| `ctx.tools.register(...)` 等 harness 注册表 | 返回的释放函数自动挂到调用插件上 |

Cordis 管不到的资源——定时器、连接、文件监视器——要自己包进 `ctx.effect()` 并返回一个释放函数：函数体在加载时运行，释放函数在卸载时运行。

插件会在什么情况下卸载？教程列了四种：**修改配置、热重载、显式释放、所需服务消失**。

每个已加载的插件实例有一个叫 **fiber** 的运行时句柄，它的状态在六种之间转换（表4-6）。

**表4-6 fiber 状态机**

| 状态 | 含义 |
|---|---|
| PENDING | 已声明，但所需服务还没就位，等着 |
| LOADING / ACTIVE | `apply` 正在运行／已完成 |
| FAILED | 加载或配置校验抛了异常 |
| UNLOADING / DISPOSED | 清理正在运行／一切已拆除 |

值得注意的是：**PENDING 是合法状态，不是错误**——提供方可能稍后才挂载。如果你的插件"不崩不报就是不干活"，先查它是不是在等谁。

## 不存在需要打补丁的特权内核

现在可以放出官方架构文档里最得意的那句：

> 不存在需要打补丁的特权内核：扩展 dsh 的方式是把插件挂载到其他插件旁边，而各项注册都是副作用，会在其插件卸载时撤销。

看清单就知道有多彻底（表4-7）：

**表4-7 dsh 里哪些东西是插件**

| 部件 | 是插件吗 | 意味着什么 |
|---|---|---|
| 模型适配器 | ✅ | 大脑可以换供应商 |
| 工具注册表 | ✅ | 工具集可以整套替换 |
| 会话日志 | ✅ | 记账方式可以换 |
| agent loop（司机） | ✅ | 驾驶逻辑可以换 |
| Web 界面 | ✅ | 界面可以不要，也可以换 |
| 沙箱与审批策略 | ✅ | 安全策略可配置 |

前四行是架构文档的原话清单——"产品的每一部分都是插件"；后两行随 `dsh-base` 和 `dsh-web-app` 组合包交付。是的，连界面都是插件。

教程还给了一个真实例子：卸载配置项 `dsh-bash-local`，挂载另一个 `shell` 提供方，所有注入了 `'shell'` 的插件会重新启动并使用新实现。换服务提供方不是做手术，是换班。

### 连注册都能分房间

插件之间平等，但"谁能看见谁的注册"可以管。术语表里有个专门的词：**scope（作用域）**——按 agent 划分的注册单位。

任何一项贡献（工具、提示词段、变量、限制、监听器）要么是**全局的**（所有 agent 可见），要么是**带作用域的**（归属于恰好一个 agent）。只有这两层，扁平结构；带作用域的注册不会向下继承给子 agent。

还有一条叫 **shadowing（遮蔽）**的规则：最具体者胜出——一个带作用域的工具或提示词段，只在它自己的 scope 里替换同名的全局项。想给某个 agent 定制专属的人设和工具变体，用的就是它。

## 连模型也能换零件

可逆性铁律让 dsh 最大胆的玩法有了登场条件：**让 agent 给自己换零件**。

官方示例 [web-cordis](https://github.com/deepseek-ai/deepseek-harness/tree/master/examples/web-cordis) 演示了：agent 可以检查当前进程的插件树，并在内存中挂载或卸载**模型写出来的插件**。它背后是一套自指工具集，给模型五个动词（表4-8）。

**表4-8 自指工具的五个动词**

| 动词 | 干什么 |
|---|---|
| `cordis_inspect` | 只读报告：谁在跑、哪些插件活着、注册了哪些工具 |
| `cordis_define` | 登记一个模型写好的包，此时什么都不运行 |
| `cordis_run` | 在沙箱里运行宿主半边，把浏览器半边投递给页面 |
| `cordis_stop` | 停止并拆干净；定义还在，可以再跑 |
| `cordis_undefine` | 必要时先停，然后忘掉定义 |

安全边界也写得清楚：动态包**只存在于进程内存里**——不创建插件文件、不安装依赖、不修改配置、不跨重启存续，stop/undefine 一喊，一切归零。

> 现实里换轮胎要停车；dsh 可以边开边换。

开发场景里还有一种更日常的"边开边换"：**热模块替换（HMR）**。HMR 插件监视文件，保存时"先卸载、再加载"——旧实例先卸载，所有 effect 回卷干净，新代码再加载进来。零件换了，车没停。

为什么这对 AI agent 尤其重要？因为 dsh 允许模型现场写插件、挂插件。模型写的东西随时可能是错的——**错了必须能一键撤销**。这是设计底线，不是事后补救。

## 组装：三明治叠层法

这么多插件，启动时怎么拼成一辆车？答案是**按层叠加**，像叠三明治（图4-2）。

![Profile 的三明治叠层](images/fig4-2-sandwich-layers.svg)

**图4-2 配置树的叠层组装**

从空桌子开始，一层一层往上叠：先叠 profile 列出的**组合包**，再叠 profile 自己的 patch 文件，再叠你家（`$DSH_HOME`）的 patch，最后叠启动时 `--patch` 指定的那层。**后叠的层永远说了算。**

这里有两个官方术语（表4-9）：

**表4-9 profile 与 bundle**

| 词 | 是什么 |
|---|---|
| profile | 存放在 dsh 之家的具名组装：列出自己叠放的组合包、存放自己安装的树外插件、保存自己的 `cordis.patch.yml`；`web` 和 `headless` 作为模板随发行版交付 |
| bundle（组合包） | Cordis 配置项及其挂载代码的分发格式——因此它插入的内容，始终可以被其上各层 patch |

每个 profile 的第一层都是 [`dsh-base`](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/base/README.zh.md)：模型适配器、工具、持久化、沙箱与审批策略、设置、凭据、遥测。[`dsh-web-app`](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/web-app/README.zh.md) 增加浏览器应用；`dsh-headless` 增加一次性运行器，且完全不带服务器。

一层 patch 干什么？**按编号（id）定位某个条目，整份替换它的配置，或者插入一个新条目。**没有整页重写这回事。

想看看自己的车到底装了些什么？不用启动，一条命令打印完整配置树：

```sh
dsh --profile web --dump-config
```

它打印出的任何一项，都可以由你自己的 patch 替换。这就是改装的入口——第 12 章的主题。

## 为什么"换零件"成立

回头看，"换零件"不是一个点子，而是三件事合在一起（表4-10）。

**表4-10 换零件的三面**

| 面 | 机制 | 结果 |
|---|---|---|
| 可换 | 服务按名字消费，消费方不导入提供方 | 配置里换提供方，消费方一行不改 |
| 可撤 | 每个注册都是 effect，卸载即回滚 | 热换件、自手术、错了能撤 |
| 可叠 | 配置按层叠加，后层按 id 修补前层 | 不动源码、不重编译，也能换零件 |

缺了任何一条，"一切皆插件"都会退化成口号。

## 📝 小结

- **Cordis 是整体搬进来的地基**——源码在 `vendor/cordis`，可审计、可打补丁、版本钉死
- **服务认名字不认人**——`ctx.tools`、`ctx.llm` 等稳定的键；消费方不导入提供方，配置选提供方
- **依赖用 `inject` 申报**——顺序由依赖决定，不由位置；服务消失，依赖方自动跟着卸载
- **可逆性是铁律**——挂载即注册、卸载即撤销；热重载和自指插件都靠它
- **没有特权内核**——模型、工具、日志、司机、界面全是平级插件；扩展 = 挂到别人插件旁边
- **组装靠三明治叠层**——组合包 → 各级 patch，后叠的说了算；`--dump-config` 可自查
