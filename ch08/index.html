    第8章 上下文工程¶

    阅读提示 大脑的书桌（上下文窗口）就那么点大。这一章看 dsh 的三个办法：桌面固定摆放、大件进仓库、旧账压成摘要。这套学问有个正式名字：上下文工程。

    书桌问题¶

    每次请求模型，dsh 都要把它"此刻需要知道的一切"摆上书桌：系统提示词、你们的对话历史、工具结果。书桌有容量上限（模型的上下文窗口），摆满就放不下新东西。

    三个经典难题（表8-1）：

    表8-1 书桌的三个难题

    难题 场景
    桌面怎么摆 每次都要带的固定内容放哪、放多少
    大件放不下 一个工具交回十万字的日志
    旧账太多 聊了一下午，前边的对话占满桌面

    第一招：桌面固定摆放¶

    每次请求前，system-prompt 零件负责拼装开场白：各个插件登记的提示词片段 + 当前可用的工具清单，按固定位置摆好。context 零件再补上工作区指令（这个项目的规矩）和时间上下文（今天几号）。

    第 5 章说过：每一步都从日志重新派生历史。所以"摆桌子"这个动作，每个步骤都会重做一遍——桌面永远是重新摆好的。

    第二招：spill，大件进仓库¶

    工具交回来的结果太大怎么办？spill 机制：

    1. 流水线关卡③（post-execute）里有一位专门的策略员，盯着超大的工具输出
    2. 他把全文原样搬进仓库（按会话隔离的本地文件）
    3. 递给模型的只有一张取货单：定位符 + 检索指引 + 文件多大

    模型拿着取货单，需要细节时再去取。大多数时候它不需要——"知道有这么个东西、知道去哪取"就够了。

    第三招：compaction，旧账压摘要¶

    对话越来越长，旧消息占着桌面。compaction（压缩）的做法：

    1. 挑出一段旧对话
    2. 请模型（单独发起一次调用）写一份摘要
    3. 桌面上，这段旧账被摘要替换

    关键的讲究在"替换"二字：日志原文一个字不删，只是被摘要"遮住"了。模型看到的是摘要，审计的人翻开日志还能看到原文。第 5 章的铁律再次生效——账本永远是完整的。

    触发方式两种（表8-2）：

    表8-2 压缩的触发方式

    方式 时机
    自动·压力 策略监测到书桌快满了
    自动·溢出 真的放不下了，紧急处理
    手动 你下命令让它现在压一次

    压缩时的"施工牌"¶

    压缩是个手术活，dsh 给它上了锁，锁的设计很能说明这团队的风格：

    • 开工前记一笔 compaction/start
    • 干完活记一笔 compaction/end
    • 如果中途崩了：有 start 没有 end——这是一块看得见的"施工牌"，下次启动能发现"上次压缩没干完"

    反过来的坏设计是：先干活、最后才记"完成"。那样中途崩溃会假装压缩已经完成。dsh 选择让失败显形，而不是让失败隐身。

    🧪 本章实验¶

    实验 8-1 ★★｜制造一次 spill 目标：亲眼看到"取货单"。 步骤：让 agent 读一个大文件（几万行的日志或源码都行），观察它收到的工具结果。 验收：结果不是全文，而是类似"内容已存到 xxx，可按需取用"的指引。

    实验 8-2 ★★｜聊到压缩发生 目标：见到压缩的账本痕迹。 步骤：和一个会话持续多轮对话，或手动触发压缩命令。 验收：日志里出现 compaction 相关事件；模型的后续回答仍能接上前文（靠摘要）。

    🤔 思考题¶

    1. ★ spill 只给模型"取货单"而不是全文——如果模型懒得去取，会出什么问题？
    2. ★ 压缩为什么宁可"遮住"原文也不删？想想第 5 章的铁律。
    3. ★★ "有 start 没 end = 施工牌"——你的工作里有没有同款"让失败显形"的设计？

    📝 小结¶

    • 书桌问题——上下文窗口有限，摆桌、大件、旧账三个难题
    • 固定摆放——system-prompt 每步重拼开场白 + 工具清单
    • spill——超大工具输出进仓库，模型拿取货单
    • compaction——旧账压成摘要替换上桌面；日志原文不删，只是被遮住
    • 施工牌设计——start/end 锁让中途失败显形，不假装成功
